# 工作流与人工确认合规设计

本文档说明"爆款内容拆解与二创 Agent"的四步工作流，以及其中保证
**真实数据**与**人工确认不可绕过**两条合规红线的具体机制。

---

## 一、状态机总览

```
INIT → RETRIEVED → ANALYZED → DRAFTED → AWAITING_APPROVAL
                                         ├─ 确认  → APPROVED → LOGGED
                                         ├─ 修改  → DRAFTED（回到生成，最多 N 轮）
                                         └─ 取消  → ABORTED
```

整个会话全程落盘 `data/sessions/<id>.json`，因此支持"分析完暂停 → 人工确认 → 再入库"的
跨进程续跑（`python main.py resume --session <id> --decision 确认`）。

---

## 二、第一步：真实数据获取与筛选

**职责模块**：`src/data_retrieval.py` + `src/providers/`

1. 解析账号定位符 `<platform>:<kind>:<value>` 为统一引用 `AccountRef`。
2. 按优先级串行尝试真实数据通道（失败自动降级）：
   - Hacker News Algolia API（免密钥，真实 points/comments）
   - Reddit / V2EX（免密钥，可能被风控）
   - Playwright 真浏览器 / 搜索 API（Serper/Tavily/博查）/ Jina Reader
3. 30 天窗口过滤；样本不足 5 条时自动扩窗并在报表中**显式标注**。
4. 分类：互动率（有曝光时）或互动总量排序，Top 1–3 为"高表现内容"，
   排除 Top 20% 后用**固定随机种子**在中位数附近抽样 2–3 条"普通内容"对照组。
5. 保存快照（含 `provenance` 溯源），保证结论可复算。

**红线：不编造数据。** 所有互动数字来自平台真实返回值；接口不提供的指标
（如转发/收藏/曝光）标为"数据不可得"，绝不填 0 冒充，也不参与计算。
快照加载时校验 `provenance`，拒绝伪造数据进入链路。

## 三、第二步：深度拆解与归因

**职责模块**：`src/analyzer.py`

### 3.1 六维打分（纯规则、可复算）
对每条内容打：选题 / Hook / 结构节奏 / 信息密度 / CTA / 互动设计（0–100 分）。
每维都可回溯到原文片段与具体指标，结论不是模型一句话。

### 3.2 差异归因（高低对比）
对高表现组 vs 普通对照组逐变量比较，输出：
- 数值型：均值差 + 效应量（归一化），按 35% / 15% 阈值分**强因果 / 疑似相关 / 噪声**；
- 布尔型：命中率差（百分点）；
- 类别型：主导取值集中度。

排序后给出**方向感知**的可执行建议——结论必须与数据方向一致。
例如"是否含数字"在高表现组反而更低时，建议是"别为凑数字牺牲可读性"，
**绝不反向建议加数字**。

### 3.3 解释力自评（防止过度归因）
主动评估"六维文本特征能解释多少真实互动差异"：
- 解释力强：六维指数差大且有多个强因果变量；
- 解释力中等：六维差小但真实互动差很大，提示选题与时机同样关键；
- **解释力弱**：两组六维几乎无差异但真实互动差几十倍——明确提示差异来自
  选题关注度、平台推荐与发布时机，**不应把功劳归给文案技巧**。

### 3.4 模板沉淀
从真实高表现样本提炼可复用"爆款内容结构模板"（模块 blocks / Hook 句式 /
CTA 句式 / 发布时段 / 自检清单）。原样本普遍缺 CTA 时，这点本身被记为
"低门槛互动型（补齐项）"——把空白当作可直接吃到的增量，而非缺陷。

## 四、第三步（上）：二次创作

**职责模块**：`src/creator.py`

围绕同一核心洞察生成 ≥3 条原创候选，覆盖三种角度：
① 反常识/冲突开场 ② 数据清单式 ③ 第一人称故事式。
- **LLM 引擎**：按模板与洞察生成（温度略高保创意）；
- **规则引擎**：无 Key 时按模板 blocks 逐段填充，保证任何环境都能产出
  结构完整、可读的候选。

生成后统一用六维引擎**反向打分**（生成即自检）。`evidence` 只取可正向复用的变量，
避免在文案里引用反向证据而自相矛盾。

---

## 五、第三步（下）：人工确认（合规核心）

**职责模块**：`src/human_review.py`

这是整条工作流**唯一的强制暂停点**，也是不可绕过的闸门：

1. `render_confirmation_sheet()` 输出《二创内容确认单》——
   核心洞察 + 关键变量表 + 可复用模板 + 候选内容 + 数据溯源与免责。
2. `wait_for_decision()` 阻塞等待人工输入，只接受 **确认 / 修改 / 取消**；
   确认时若附编号（如 `确认 1,3`）只入库指定候选。
3. 只有 `decision == confirm` 时才签发 `ApprovalToken`，
   token 内含候选内容的 **sha256 摘要**与操作人、时间。

> 提示语（题目指定文案）：
> "分析已完成。请审核生成的候选内容。输入 '确认' 将内容写入资产库，输入 '修改' 重新调整。"

**配置层面无开关**：`Settings.require_human_approval` 是 `init=False` 的常量，
无法通过环境变量关闭。

---

## 六、第四步：资产入库与记录

**职责模块**：`src/asset_store.py`

写入前调用 `HumanReviewGate.assert_approved(token, drafts, session_id)` 做最终闸门校验：
- token 为 `None` → 拒绝；
- `decision != confirm` → 拒绝；
- `session_id` 不匹配 → 拒绝；
- 待写入内容与 token 摘要不一致（确认后被篡改）→ 拒绝。

任意一项不满足都会抛 `HumanApprovalRequired`，**一条也写不进去**。
入库记录含资产 ID、来源账号、模板名、核心洞察、确认人、凭证摘要，以及
`tracking` 字段（发布后回填真实表现，待后续追踪）。

支持三种后端：`json`（默认，零配置）/ `notion` / `feishu`，由 `ASSET_BACKEND` 切换。

---

## 七、端到端防绕过小结

| 风险 | 防护 |
| --- | --- |
| 编造互动数据 | 只取平台真实值，缺失标"不可得"，不填 0 |
| 伪造快照入链路 | 快照校验 `provenance`，缺溯源直接拒绝 |
| 跳过人工确认直接入库 | `commit()` 强制 `assert_approved()`，无凭证抛异常 |
| 确认后篡改内容再入库 | `ApprovalToken` 含内容 sha256，摘要不一致拒绝 |
| 过度归因误导 | 解释力自评，弱解释力时明确提示选题/时机主导 |
| 人为关闭确认 | 配置无开关，常量固定为 `True` |
